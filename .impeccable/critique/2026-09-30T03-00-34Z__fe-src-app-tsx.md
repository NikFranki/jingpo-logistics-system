# Critique: fe/src/App.tsx

## Design Specificity Verdict
The interface has a real logistics workflow inside a mostly generic enterprise shell. Shipment stages, A → B / B → C routes, simulation time, and delay states are specific to this product. The light canvas, blue primary actions, pale status tags, Pro tables, and drawers follow conventional Ant Design patterns, so the product identity is recognizable but not distinctive. The source review was not paired with a usable visual overlay.

## Cognitive Load
One likely checklist failure: minimal choices. Simulation selectors can load up to 100 shipments or tasks at once. Search helps, but options are not grouped or paged in the component. Navigation has three destinations and each selected item exposes a small action set; creation forms use progressive disclosure.

## Emotional Journey
The persistent demo clock and explicit stage labels help users trust that the system is grounded in its simulation. Confidence drops at disabled controls because the reason is only available as a hover title. Mistaken state-changing actions have no clear recovery. Creating an order/task and opening its detail is a useful completion point.

## What's Working
- The three primary destinations map clearly to orders, transport tasks, and simulation controls.
- Route, timezone, and backend validation rules appear near relevant actions.
- Loading, error retry, and success feedback cover the main data flows.

## Priority Issues
1. **P1 — Disabled simulation actions provide limited guidance.** Reasons are only in `title`; the general backend-validation notice does not say what to do next. Show the specific reason and next eligible step inline. Suggested command: `$impeccable clarify`.
2. **P1 — Simulation actions have no visible reversal path.** Clock advancement, task departure/arrival, and shipment events change state. Define reset, confirmation, or undo behavior for live demos before implementation.
3. **P2 — The core flow spans three destinations.** Order, shipment, task, and event progression requires switching among Orders, Tasks, and Simulation. Keep the current entity context and next action visible. Suggested command: `$impeccable shape`.
4. **P2 — Selectors have a 100-record ceiling.** Simulation loads only the first 100 shipments and tasks; task candidates are also capped at 100. Older records become unreachable as data grows. Suggested command: `$impeccable optimize` plus backend pagination/search support.
5. **P2 — Narrow-screen table use needs validation.** The Orders table scroll width is 980px, so status and action columns may require horizontal searching on phones. Responsive CSS exists, but no physical-device validation was available. Suggested command: `$impeccable adapt`.

## Persona Red Flags
- **Alex, power operator:** no visible batch controls or shortcuts; per-record operations add repetitive work.
- **Jordan, first-timer:** “揽收,” “入站,” and fixed area Z assume domain knowledge; disabled-action reasons are not persistent.
- **Sam, keyboard/accessibility user:** menu and detail actions use `<a>` elements with click handlers and no `href`; keyboard reachability and announced semantics need verification.
- **Riley, stress tester:** only the first 100 records are selectable and simulation changes have no visible rollback.

## Minor Observations
- The 980px table scroll width can move status and operations off-screen on narrow devices.
- The order’s next step, shipment creation, is only visible after opening its detail drawer.
- Density, column settings, and refresh are useful but add secondary controls to a simple table task.

## Questions to Consider
- Should Simulation behave more like an operator console or a guided demo?
- What recovery story should a presenter have after advancing the clock or triggering the wrong event?
- Which detail should be recognized at a glance: route progression, shipment stage, or delay risk?
