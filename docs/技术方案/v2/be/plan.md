# JINGPO 后端 V2 · 分步实施计划

> 2026-09-29 · 草案。依据 [V2 PRD](../../../prd/v2/JINGPO-logistics-system-v2.md) 和 [spec](spec.md)。本计划拆分实施工作，不表示任何步骤已完成。

## 1. 实施原则

V2 先在固定 A/B/C、AB/BC 网络上完成模型替换。各步在隔离分支和测试库验证；阶段与事件切换相关步骤完成前，不把中间状态部署到共享环境。代码、迁移和客户端契约必须作为一次可运行的切换交付。使用独立 PostgreSQL 测试库及 V1 数据副本，开发库不作为清理型测试库。步骤可以继续拆小，完成当前步骤并记录验证证据后再推进下一步。

当前仓库已有 `be`、`agent`，以及尚未纳入 Git 的 `fe` 工作目录；实施时先确认前端是否作为 V2 交付物纳入版本控制。不要在文档阶段改动这些业务代码。

## 2. 分步路线

| 步骤 | 主要工作 | 本步验证 | 对应规格 |
| --- | --- | --- | --- |
| V2-S01 | 盘点 BE、前端、Agent 对旧阶段/事件的引用；细化首次入站请求和 `active_transport_task` 响应契约 | 列出旧值引用清单、迁移映射和客户端字段示例 | V2-01/03/07 |
| V2-S02 | 用 V1 样本构造迁移演练数据库；检查旧阶段、事件、站点、任务和幂等缓存的真实组合 | 对不一致样本报错；记录迁移前行数、事件 ID 和关键响应 | V2-06 |
| V2-S03 | 增加集中定义的阶段/事件枚举及业务规则；运输任务仍按固定网络运行，先覆盖新建数据路径 | 新运单揽收后无站点；首次 A 入站单独成功；候选和派送边界正确 | V2-01/02/03 |
| V2-S04 | 将任务发车、到达规则改为通用阶段和事件；修正多次 `ARRIVE`/`DEPART` 的业务防重 | 同一运单完成 AB、BC；重复发到不增轨迹；批量故障整体回滚 | V2-03/04/05 |
| V2-S05 | 编写并审查 Alembic 迁移：映射历史值、替换 CHECK 约束、处理幂等缓存兼容；制定备份和回退步骤 | V1 副本升级后历史 ID、时间、关联不变；旧 key 重放符合 V2 响应 | V2-06 |
| V2-S06 | 更新 BE 列表/详情/筛选及 `allowed_actions`；显式提供当前任务/线路信息，保留最后扫描站点的准确含义 | 在站和运输中的响应均可解释，前端不需推测当前线路 | V2-01/07 |
| V2-S07 | 更新前端阶段标签、轨迹文案、首次入站参数和操作按钮；展示订单原地址与运单执行地址 | A→B→C 页面全流程；两类地址有明确标签；非法操作禁用且后端拒绝 | V2-02/07/08 |
| V2-S08 | 更新只读 Agent 的响应校验、筛选枚举、提示和场景测试 | 能区分当前任务和历史任务，不把最后扫描站点称为实时位置 | V2-07 |
| V2-S09 | 联合验收与迁移复演：新库、V1 数据副本、正常/失败/幂等/并发/延误链路；记录版本切换说明 | V2-01～08 全部有证据；旧客户端契约变化已列明 | V2-01～08 |

S03～S06 的实现顺序可按迁移方式微调，但数据库约束、服务逻辑和响应模型必须作为一次可运行的切换交付；不能在共享环境长期保留两套相互冲突的阶段语义。每一步若超过可审阅范围，拆成 a/b 小步并写明完成条件。

## 3. 本轮文档之后的第一步

V2-S01 先产出一页契约表：旧值 → 新值、首次入站请求样例、运单详情的当前任务字段样例、前端与 Agent 的受影响位置。用这张表复核“揽收 ≠ 首站入站”“订单地址不回写”和“运输中最后扫描站点不是实时位置”。此步只确定契约与测试样本，不做数据库迁移。

## 4. 验证记录模板

每步记录：目标、修改文件及原因、迁移前提、请求/数据流、成功与失败样本、执行命令和结果、对应 V2 验收编号、遗留问题。未执行的验证只写“待验证”，不写成已通过。
