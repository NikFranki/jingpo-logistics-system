# JINGPO 后端 V1 · 开发规格

> 2026-09-21 · 供评审。本文定义后端最终必须满足的行为与验收条件，不代表已实现。

实现前用本文核对需求，实现后按验收条目检查结果。它不是代码生成提示词，也不授权一次性完成整个后端。

## 2. 范围与技术边界

首版提供独立后端，通过 `/docs` 或 HTTP 客户端演示卖家 → A → B → C → 买家签收。没有前端也必须能够验收完整业务。

- Python + FastAPI + Uvicorn；Pydantic 定义输入输出。
- PostgreSQL + SQLAlchemy + Psycopg 3，同步 Session 与普通 `def` 路由；Alembic 管理结构变更。
- 单个本地业务服务、单个演示操作人；固定 A/B/C、AB/BC、区域 Z。
- 不包含 Agent、登录权限、动态路由、车辆司机管理、部分到货、异常工单、支付库存和退货。
- uv、Docker Compose 等可选工具不作为当前学习或启动的前提。

## 3. 可验收的业务规格

| 编号 | 必须满足的行为 | 验收示例 |
| --- | --- | --- |
| BE-01 | 服务可运行并提供接口文档；数据库可用性可单独检查 | `/health` 返回成功；数据库不可用时 `/health/ready` 返回 503 |
| BE-02 | 创建、查询、按阶段编辑订单；编号由后端产生 | 正常订单持久化；空地址或数量非正整数返回 422；不存在的 ID 返回 404 |
| BE-03 | 一订单最多一运单；创建运单后订单锁定 | 两次发货返回同一运单；创建后编辑订单返回冲突 |
| BE-04 | 运单地址是独立快照，仅揽收前可改 | 修改运单地址不回写订单；保存前后值；揽收后拒绝修改 |
| BE-05 | 运单通过事件按既定阶段推进，轨迹只追加 | 跳站、提前签收被拒绝；同一演示时间下轨迹按写入 ID 排序 |
| BE-06 | 任务仅能关联起点站内且未占用的运单 | AB 选 A、BC 选 B；空清单、重复 ID、错误阶段或已占用均被拒绝 |
| BE-07 | 创建任务要求 ETA 晚于当前演示时间，创建后不可编辑、取消、删除 | 创建后运单仍在起点；没有修改线路、ETA 或运单清单的业务入口 |
| BE-08 | 发车与合并到达批量更新任务和全部关联运单 | 到达时一次完成任务、入站、释放占用、轨迹与成功日志；任何一步失败全部回滚 |
| BE-09 | C 入站后派送，派送后签收，签收联动订单完成 | 提前派送或签收失败；正常签收后运单和订单同步完成 |
| BE-10 | 演示时钟持久化，仅支持增加 30 或 120 分钟 | 初始为北京时间 2026-09-20 08:00；推进不自动发车到达；重启不重置 |
| BE-11 | 仅 AB 显示超时与晚到；提示不改变物流状态 | AB 运输中超过 ETA 提示超时，到达后保留晚到分钟数；等于 ETA 不超时；BC 不提示 |
| BE-12 | 写请求支持幂等重试及业务防重 | 同 key 同内容重放成功结果；同 key 不同内容返回 409；重复物流动作不重复写轨迹 |
| BE-13 | 并发操作不能绕过业务约束 | 两任务争抢一运单仅一个成功；揽收与地址修改按锁定顺序校验执行 |
| BE-14 | 查询提供页面后续所需数据和操作条件 | 列表筛选分页；详情含关联信息、最后扫描站点、轨迹或时间、allowed_actions 与禁用原因 |
| BE-15 | 初始化和失败处理可预测 | 初始化可重跑且不重置时钟；失败响应含稳定错误码与 request_id；日志不暴露完整地址或密码 |

运单阶段：`PENDING_PICKUP → PICKED_UP → AT_A → IN_TRANSIT_AB → AT_B → IN_TRANSIT_BC → AT_C → OUT_FOR_DELIVERY → SIGNED`。

任务阶段：`PENDING_DEPARTURE → IN_TRANSIT → ARRIVED`。占用关系和超时提示都不新增物流阶段。“最后扫描站点”不代表运输中的实时位置。

## 4. 必须保持的一致性

- 一个业务写操作一个事务；Session 不跨请求共享，模块内部不得分段 commit。
- 首版所有业务写入先锁定单条 simulation_settings，再检查最新状态；在事务提交或回滚时释放。
- 数据库唯一约束防止重复运单、重复任务关联和重复幂等记录；不能仅依赖前端按钮禁用。
- 成功日志、幂等响应与业务变更一起提交；失败后业务回滚，失败原因写服务日志。
- 一次用户操作使用一个 Idempotency-Key，重试复用；创建订单、任务和推进时钟不能根据“请求看起来相似”去重。
- 演示时间用于业务事件；真实时间用于创建、更新和请求记录。刷新后的延误由后端计算，不依赖浏览器时钟。
- 共 8 张业务表与 1 张演示配置表。完整 SQL 见技术方案 3.1–3.3，逐阶段迁移，不一次性生成全部模型。

## 5. 接口契约与验证依据

沿用技术方案第 7 节，不自行改名：例如创建接口为 `POST /api/v1/orders/create`、`POST /api/v1/transport-tasks/create`。ID 输出字符串，时间带时区，JSON 字段采用 snake_case。

业务错误使用技术方案中的统一结构；区分 404 不存在、409 冲突、422 输入错误、503 暂不可用和 500 未预期错误。不将数据库堆栈作为用户提示。

每个已实现条目记录可重复的操作和结果。业务测试使用独立 PostgreSQL 数据库，重点检查状态、唯一约束、事务回滚和并发，不能只检查 HTTP 200，也不能使用开发数据库清理测试数据。

## 6. 学习与协作要求

用户需要理解后端知识及代码演进，不能仅获得一套已完成的代码。

1. 每次只推进 plan.md 中一个小步；若仍过大，继续拆小。
2. 动手前说明目标、文件职责、请求路径和预计变更范围。
3. 只创建当前确有用途的文件；不预建空模块、不提前写后续业务、不引入无需求的抽象。
4. 变更后说明每个新增文件为什么需要、已有文件如何变化，并提供用户可亲自操作的验证步骤。
5. 解释设计原因及失败场景，不只讲 Python 语法。
6. 完成本步后等待用户确认再进入下一步；本步必要的修复和验证可以继续完成。
7. 当前由单个 Agent 串行协作，未获用户明确要求不进行多 Agent 编码。

## 7. 完成定义

V1 完成需要 BE-01 至 BE-15 均有验证证据，完整物流链路和 AB 超时场景能通过接口复现；迁移与初始化可重现，重启后数据可恢复。还需说明文件职责及关键请求的调用路径，并完成用户评审。

中间阶段可以仅实现部分规格，但必须明确当前支持范围；未接入事务、防重的练习函数不作为完成的业务写接口交付。文档存在、代码可启动或某一步通过，都不等于 V1 已完成。
